## Behaviour now explained

- Removed scenarios retain labels and provenance, but their obligations are excluded from active analysis. A usable removed rule can help identify a gap for an event that still has a surviving conditional response; the finding records `opened_by`. Removing the last response to an event is treated as retirement.
- Scenarios inside a modified requirement are matched by name and normalized text. An unchanged sibling is not automatically blamed for the change. This is textual matching, not proof of semantic equivalence.
- Optional `--incremental` mode reuses a formalized base and translates added or rewritten scenarios. Solver analysis runs on the combined active model. Full formalization remains the default.
- The current cache checks generated base text and model name. Cached vocabulary and interpretations stay fixed. A changed base, including a change archived into it, requires another base build.

## Limits kept explicit

Incremental extraction currently follows scenarios. Changing only a requirement's SHALL sentence while leaving its scenarios unchanged, or adding a requirement without scenarios, can emit no new incremental text and reuse the old model. Full mode is needed for these edits; there is no automatic fallback. Cache identity also omits sample count, temperature, endpoint, model weights, prompts and code version.

The same solver procedure does not make the two modes equally accurate: the encoded interpretation can differ. Existing temporal/entity limits, finite search limits and uncertainty in translation remain. Passing offline tests does not measure natural-language accuracy on independent projects.
